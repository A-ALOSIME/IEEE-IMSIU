## 1. الغرض والمراجع

نصمم جهة الإدارة كمنتج واحد متماسك في ست مناطق، ثم نجري مراجعة مجمعة ونثبت التصميم قبل الربط النهائي والـQA. البداية: **Sidebar + Topbar + Overview**، ثم بقية الشاشات باللغة البصرية نفسها.

هذا الملف يلخص ما يحتاجه المصمم: الشاشات، البيانات الظاهرة، الإجراءات، الصلاحيات والحالات. لا يستبدل مواصفات المشروع ولا يكرر المعمارية أو قاعدة البيانات أو إعداد الخدمات.

- مصدر القرارات: [IEEE-IMSIU-WEBSITE-SPEC.md](sources/IEEE-IMSIU-WEBSITE-SPEC.md)، خصوصًا الأقسام 7–17.
- مرجع بصري قائم: [Home High-Fidelity](<sources/IEEE-IMSIU-Home-High-Fidelity(2).html>)، مع هوية النادي الحالية.
- المحتوى العام الواقعي: الملف التعريفي، سجل الأعمال والإنجازات، و[tweets.md](sources/tweets.md). التغريدات مرجع تاريخي مساعد؛ لا تتغلب على المواصفات أو السجل المنظم.
- اتفاق المحادثة «تحديد مرحلة موقع IEEE IMSIU»: ست مناطق، بيانات واقعية، مراجعة واحدة بعد اكتمال الأدمن، ثم تثبيت التصميم والتنفيذ والـQA؛ README بعد استقرار المشروع.

**قاعدة البيانات في التصميم:** نستخدم أسماء الفعاليات والصور والمعلومات العامة الموثقة. بيانات الطلاب والمسؤولين والبريد والعضوية والساعات أمثلة اصطناعية موسومة بوضوح؛ لا نخترع إجماليات ونقدمها كأرقام فعلية. حالة التسجيل التاريخية لا تعني أن الفعالية مفتوحة اليوم.

## 3. نظام الواجهة المشترك

- **الإطار:** Sidebar ثابت على سطح المكتب وقابل للفتح على الجوال؛ Topbar للعنوان/المسار، اللغة، الثيم، هوية المستخدم ودوره والخروج. يظهر التنقل وفق الصلاحية.
- **اللغة والثيم:** العربية افتراضيًا وRTL أصيل، مع الإنجليزية وLTR؛ System / Light / Dark. الأرقام والتواريخ تستخدم 0–9 في اللغتين. الوضع الفاتح بخلفية رمادية محايدة، أسطح بيضاء وتباين واضح، مع الحفاظ على ألوان الهوية والشعار الأصلي. صمم Light وDark فعليًا، واحفظ وضوح الأرقام والبريد والروابط داخل RTL.
- **الهوية:** الأزرق `#2F6D9E`، البنفسجي `#51326C`، الدرجات المساندة `#9DBDDE` و`#B3A9D3`، Accent محدود `#9A2583`. العناوين Vazir والنص Almarai والإنجليزية/الأرقام Open Sans أو بدائل معتمدة؛ لا تعد الألوان والخطوط النهائية مثبتة قبل مراجعة النظام المشترك.
- **المكونات:** عنوان صفحة ووصف قصير وإجراء رئيسي؛ أزرار أساسية/ثانوية/خطر؛ Tabs؛ حقول ونص مساعدة وخطأ؛ Select؛ شارات حالات بنص؛ Date/Time؛ Upload ومعاينة وتقدم وخطأ؛ جداول؛ Pagination؛ حوار تأكيد؛ Toast؛ Skeleton؛ Empty state.
- **الجداول:** بحث وفرز وفلاتر مناسبة، عدد النتائج، صف قابل لفتح التفاصيل، اختيار فردي وجماعي وشريط إجراءات للمحددين. يوضح التحديد هل يشمل الصفحة أم النتائج المفلترة؛ لا يوحي بتحديد بيانات غير محددة فعليًا.
- **التفاصيل والنماذج:** ملخص واضح ثم مجموعات حقول؛ الحفظ منفصل عن النشر أو الإرسال. إظهار الحقول المطلوبة والتحقق قربها، وحماية التعديلات غير المحفوظة عند المغادرة.
- **التجاوب والوصولية:** تصميم للجوال والتابلت وسطح المكتب، أولوية الأعمدة المهمة وإتاحة البقية؛ التركيز المرئي ولوحة المفاتيح وتسميات الحقول والتباين والنص البديل. لا يعتمد المعنى على اللون وحده.
- **الأسلوب:** مساحات وتسلسل بصري واضحان، جداول عملية وحركة خفيفة، دون إفراط في البطاقات أو gradients أو الزخرفة. لا نضيف بحثًا عامًا أو مركز إشعارات كاملًا بلا احتياج معتمد.

## 5. Overview

شاشة تشغيلية مختصرة، تعرض ما يستدعي عملًا بحسب الدور:

- الفعاليات المفتوحة وعدد التسجيلات الجديدة، مع الانتقال إلى المسجلين.
- طلبات العضوية التي تحتاج مراجعة، مع رابط الدورة والطلبات.
- آخر المقالات والمسودات للمصرح له، مع متابعة التحرير.
- نتائج البريد المهمة، خصوصًا الفشل، مع فتح تفاصيل الدفعة.
- مؤشرات تشغيلية محدودة من بيانات النظام، دون رسوم للحشو.

تختفي بطاقات الأعداد الصفرية للمهام والملخصات التشغيلية غير النشطة تلقائيًا، ولا تُعرض دورات خالية أو فعاليات مؤرشفة لمجرد ملء المساحة؛ تبقى الأقسام متاحة في القائمة حسب الصلاحيات. يُصمم أيضًا وضع «لا توجد مهام معلقة». لا تعرض بيانات العضوية لمحرر المحتوى ولا تتحول Overview إلى نسخة مكررة من Analytics.

## 6. Events / Registrations

| الشاشة | البيانات والإجراءات اللازمة |
| --- | --- |
| قائمة الفعاليات | العنوان/الصورة، الموعد، النشر، التسجيل، العدد/السعة عند وجودها؛ بحث وفلاتر، إنشاء، تعديل، Duplicate Event |
| إنشاء/تعديل فعالية | عنوان ووصف وصورة كاملة دون قص وبنسبتها الأصلية، تاريخ ووقت البداية وتاريخ ووقت الانتهاء، موقع أو رابط حضور، النشر، وضع التسجيل، فتح/إغلاق ومواعيدهما، السعة، قائمة الانتظار؛ حفظ مسودة ومعاينة ونشر، تثبيت لـSuper Admin |
| نموذج التسجيل | اختيار قالب، إضافة/حذف/ترتيب الحقول، مطلوب/اختياري، شروط الظهور، معاينة وحفظ/نسخ الإعداد |
| المسجلون | الاسم والتواصل، وقت الطلب، الحالة؛ البحث والفرز والتصفية، تفاصيل الإجابات/الملفات، تغيير الحالة فرديًا وجماعيًا، CSV، Email selected |
| المشاركة | نسخ الرابط، QR وتنزيل PNG/SVG، التقويم ومعاينة بطاقة المشاركة؛ رابط ثابت/تحويل ووجهته وتعطيله وفق المواصفات والصلاحية التي تُحسم |

**أوضاع التسجيل:** لا تسجيل، تسجيل مباشر، تقديم يحتاج مراجعة. **قوالب البداية:** تسجيل سريع، فعالية طلابية، تقديم/سعة محدودة، نموذج مخصص فارغ.

المحرر المشترك يدعم: نص قصير/طويل، بريد، جوال، رقم، قائمة، اختيار واحد/متعدد، إقرار، رفع ملف. تعرض الحقول الإضافية في التفاصيل بدل تكديسها في الجدول.

افصل حالات النشر (مسودة/منشورة/غير منشورة) عن زمن الفعالية (قادمة/سابقة) وعن التسجيل (قريبًا/مفتوح/مكتمل/انتظار/مغلق/انتهت). حالات الطلب الموحدة للفعاليات والنادي: بانتظار المراجعة قبل القرار، ثم مقبول، غير مقبول، أو قائمة انتظار. أزرار القبول والرفض والانتظار لكل طلب دون تحديده أو اختيار حالة من قائمة؛ وتبقى الأزرار الجماعية للمحدد مع تأكيد العدد، والبريد منفصل.

**التدفقات:** إنشاء من قالب ← إعداد التفاصيل والنموذج ← معاينة ← نشر. مراجعة طلب ← تغيير الحالة ← اختيار المستلمين ← البريد عند الحاجة. تغيير حالة الطلب لا يرسل رسالة تلقائيًا. فتح/إغلاق التسجيل يدويًا إجراء مباشر لـHR، مع توضيح الموعد التلقائي. النسخ لا يوحي بنسخ تسجيلات الأشخاص.

حالة الطلب منفصلة عن العضوية. حالات العضو المتوقعة: نشط، غير نشط، غادر، أزيل؛ يفضل تغيير الحالة للحفاظ على التاريخ. إجمالي الساعات ناتج من القيود وليس رقمًا يُحرر مباشرة.

**التدفق:** دورة قبول ← طلبات ← ضغطة زر قبول ← قبول الطلب وإضافة العضو معًا في لجنته المختارة ← تسجيل الساعات. إرسال البريد خطوة منفصلة وصريحة. القبول الجماعي يضيف المقبولين إلى الأعضاء دون إرسال تلقائي. التخصصات: علوم الحاسب، نظم المعلومات، تقنية المعلومات؛ لا نطلب مستوى الدراسة. لا نصمم مسار اعتماد ساعات متعدد المراحل قبل حسمه.

الترتيب الافتراضي للساعات من الأعلى إلى الأقل، في سجل الساعات وإجمالي ساعات الأعضاء؛ يظل فلتر العضو متاحًا، مع إمكانية الترتيب تصاعديًا أو بالتاريخ.

## 8. Content — Articles / Announcements

**Articles:** قائمة بعنوان المقال والكاتب والتصنيف واللغة والحالة وتاريخ النشر/التحديث، مع البحث والتصفية والتحرير والمعاينة. محرر Rich Text عربي يدعم العناوين والقوائم والروابط والصور؛ عنوان ووصف مختصر وغلاف ونص بديل، صور داخلية، الكاتب والتصنيف، وسوم عند الحاجة، Slug، بيانات SEO وبطاقة المشاركة، حقول عربية/إنجليزية.

التدفق: مسودة ← معاينة ← نشر ← إلغاء نشر/أرشفة عند الحاجة. تظهر بيانات آخر تعديل بسيطة؛ لا تاريخ مراجعات مؤسسي. يتيح التصميم تحرير الإنجليزية وحالة عدم توفر ترجمة، دون وعد بتوليد آلي قبل اختيار المزود. RSS نتيجة نشر المحتوى، وليس شاشة إدارة مستقلة.

**Announcements — Super Admin فقط:** قائمة وحوار/نموذج إنشاء وتعديل؛ عنوان ونص قصير ورابط/زر اختياري وحالة التفعيل. تفعيل/تعطيل يدوي ومعاينة موضع الظهور وإزالة مع تأكيد. جدولة البداية والنهاية مؤجلة؛ لا نضيفها للنموذج الحالي.

التثبيت في الصفحة الرئيسية إجراء لـSuper Admin. الإعلانات مستقلة عن الفعاليات والمقالات ولا تدخل RSS عادة.

## 9. Analytics — Super Admin

- نطاق زمني 7/30/90 يومًا، مع بيان مصدر البيانات وحداثتها.
- عامة: الزوار، مشاهدات الصفحات، أبرز الصفحات/المحتوى، مصادر الزيارات، الجوال مقابل سطح المكتب واتجاه الزيارات.
- تشغيلية: تسجيلات حسب الفعالية والحالة، طلبات حسب الدورة والحالة، الأعضاء والساعات، نتائج البريد المتاحة.
- رسوم قليلة تخدم المقارنة، مع أرقام وتسميات واضحة. لا تخلط الحضور التاريخي الموثق بتسجيلات النظام، ولا تربط الزيارات بهوية الطلاب.
- مؤشرات Web Analytics مرغوبة؛ طريقة إتاحتها داخل الأدمن تحتاج تحققًا وقت الربط. صمم حالة «البيانات غير متاحة» بدل أرقام مصطنعة أو وعد بتكامل لم يُثبت.

## 10. Team Access — Super Admin

قائمة المسؤولين: الاسم عند توفره، البريد المعتمد، الدور وحالة الوصول. نموذج إضافة بريد معتمد واختيار أحد الأدوار الثلاثة، ثم تعديل الدور أو تعطيل/إزالة الوصول مع تأكيد واضح يذكر المستخدم والأثر.

Cloudflare Access يثبت الهوية والتطبيق يحدد الصلاحية؛ لا يوحي النموذج بأن حفظ الدور وحده يضبط بوابة Access. طريقة مزامنة السماح بالدخول وحالة الوصول تُحسم عند الربط. لا نفترض إرسال دعوة بريدية أو نبني إدارة كلمات مرور. الإعدادات العامة والتكاملات تبقى حقًا لـSuper Admin، وتفاصيل شاشاتها خارج هذا المرجع حتى يُحدد احتياج التصميم.

## 11. Email selected — تدفق مشترك

يستخدمه HR أو Super Admin داخل التسجيلات وطلبات العضوية، وفي سياق الأعضاء عند الحاجة للصلاحية نفسها:

1. تحديد السجلات: عدد واضح ومصدر المجموعة وإمكانية مراجعة المستلمين.
2. Email selected: اختيار قالب محفوظ أو رسالة مخصصة.
3. تحرير العنوان والنص والروابط والصورة الاختيارية، مع اسم المستلم عند توفره وهوية النادي.
4. Preview: معاينة المحتوى والمستلمين والعدد؛ لا تعني المعاينة إرسالًا.
5. تأكيد صريح للإرسال، مع منع الضغط المتكرر أثناء التنفيذ.
6. نتيجة الدفعة ونتيجة لكل مستلم حسب المتاح: Sent / Delivered / Failed. Sent لا يعني Delivered؛ الحالة غير المتاحة لا تُعرض كنجاح مؤكد.

القوالب الأولية: قبول عضوية، قبول معسكر، قبول ورشة/فعالية، قائمة انتظار، تعليمات قبل الفعالية. إظهار البريد المفقود/غير الصالح والفشل الجزئي وعدد الحالات الناجحة والفاشلة؛ لا نعيد إرسال دفعة كاملة تلقائيًا عند الخطأ. عنوان المرسل النهائي غير محسوم حتى اعتماد الدومين.

لا بريد تلقائي لكل تسجيل بسيط، ولا نظام حملات أو Newsletter. WhatsApp مساعدة يدوية مثل فتح رسالة فردية أو التصدير؛ لا إرسال جماعي آلي.

## 12. الحالات المشتركة

## 13. حدود النطاق والنقاط غير المحسومة

**لا نضيف:** حسابات طلاب أو بوابة عضو، دور Event Manager، CRM، حملات/Newsletter، WhatsApp API، مزامنة Sheets، Audit مؤسسي، منشئ تقارير عام، أو أتمتة متعددة المراحل. CSV هو مسار التصدير؛ لا نعيد شرح البنية التقنية هنا. GitHub ليس شرطًا لإنجاز التصميم.

**تحتاج حسمًا قبل تصميم التدفق المعني نهائيًا:** اعتماد/مراجعة الساعات، QR الحضور، سياسة الاحتفاظ والحذف، أنواع وأحجام الملفات، طريقة تكامل Analytics، سياسة الترجمة ومزودها، الربط بين Team Access وبوابة الدخول، صلاحيات إدارة روابط التحويل ومسميات الحالات النهائية. لا تنشئ هذه النقاط ميزات جديدة تلقائيًا، ولا تمنع تصميم بقية النطاق المحسوم.

بعد اكتمال الشاشات: مراجعة مجمعة لأهم مشكلات UX والترتيب والتدفقات، ثم تثبيت التصميم. التغيير بعد التثبيت يعالج مشكلة فعلية أو قرارًا صريحًا، دون دوامة تحسينات شكلية.

## 16. تبسيط قرارات القبول

تسجيلات الفعاليات وطلبات النادي تستخدم أزرارًا واضحة ومباشرة: قبول، رفض، قائمة انتظار؛ الفردي دون حوار تأكيد أو قائمة تغيير حالة. الحالة المرفوضة «غير مقبول»، والحالة الأولية «بانتظار المراجعة». قبول النادي ينشئ سجل العضو تلقائيًا دون تكرار؛ الطلب المرتبط بعضو لا يتحول إلى رفض يتسبب بإزالة العضو، بل تُدار حالة العضو من الأعضاء. الإجراءات الجماعية تبقى متاحة بأزرار مماثلة مع تأكيد العدد. لا يُرسل البريد تلقائيًا عند اتخاذ القرار.
